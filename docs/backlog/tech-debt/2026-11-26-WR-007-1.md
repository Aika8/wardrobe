# WR-007: two changes of the same item at once can both pass the status check

`ChangeStatus.change` does find → `withStatus` → `replace` as three catalogue calls. Each call is locked in
`InMemoryItemCatalog`, but the sequence is not: two requests on the same item (say CLEAN→IN_WASH and
CLEAN→ON_TRIP) can both read CLEAN, both pass the table, and the later `replace` wins — an ON_TRIP item that
skipped nothing illegal, but the IN_WASH change is silently lost. Different items are safe (tested). Possible fix:
a compare-and-replace on the port (`replace(expected, changed)`), or optimistic versions when real storage comes.
